# Study Notes 낙관락-동작방식-코드

## 17:48:10

### Question
낙관락 구동방식이랑 실제 코드가 어케 작동하는지 궁금함

### Answer
현재 코드의 낙관락은 `JPA @Version`과 `If-Match` 헤더를 함께 쓰는 형태입니다.

핵심은 두 단계입니다.

1. 엔티티 레벨 JPA 낙관락
- `Review` 엔티티에 `@Version`이 붙은 `lockVersion` 컬럼이 있습니다.
- `Task` 엔티티에도 `@Version`이 붙은 `lockVersion` 컬럼이 있습니다.
- JPA는 엔티티를 업데이트할 때 `where id = ? and lock_version = ?` 같은 조건으로 업데이트를 시도하고, 성공하면 `lock_version`을 1 증가시킵니다.
- 만약 다른 트랜잭션이 먼저 수정해서 `lock_version`이 바뀌었다면, 현재 트랜잭션의 update 대상 row 수가 0이 되고 낙관락 충돌로 봅니다.

2. API 레벨 사전 충돌 검증
- 현재 리뷰 본체를 바꾸는 API는 `If-Match` 헤더로 클라이언트가 보고 있던 `lockVersion`을 같이 보냅니다.
- 컨트롤러에서 `@RequestHeader("If-Match") Long lockVersion`으로 받습니다.
- 서비스의 `validateLockVersion(review, lockVersion)`이 DB에서 읽은 현재 리뷰의 `lockVersion`과 헤더 값을 비교합니다.
- 다르면 저장 전에 바로 `REVIEW_VERSION_CONFLICT`를 던집니다.

실제 흐름은 대략 이렇습니다.

```text
클라이언트가 리뷰 조회
-> 응답에 lockVersion 포함
-> 수정/승인/반려/취소 요청 시 If-Match로 같은 값 전송
-> 서비스가 DB의 현재 review.lockVersion과 비교
-> 같으면 비즈니스 로직 수행
-> JPA가 UPDATE ... WHERE lock_version = ? 수행
-> 성공 시 lockVersion 증가
```

예를 들어 승인 API는 다음 순서로 동작합니다.
- 컨트롤러가 `reviewId`와 `If-Match`를 받음
- `ReviewCommandService.approveReview(...)` 호출
- 서비스가 `loadReview()`로 현재 리뷰를 읽음
- `validateSubmittedReview()`로 상태가 `SUBMITTED`인지 확인
- `validateLockVersion()`으로 헤더 값과 현재 DB 값을 비교
- 승인 권한 체크
- `review.approve(...)`로 상태 변경
- 트랜잭션 종료 시 JPA가 `@Version` 기준으로 update

그래서 지금 구조의 장점은 다음입니다.
- 사용자가 오래된 화면에서 수정/승인하면 서비스 레벨에서 바로 막을 수 있음
- 혹시 같은 시점에 저장이 겹쳐도 JPA `@Version`이 마지막 보호막 역할을 함
- 즉 "API 사전 검증 + JPA 최종 검증" 두 겹으로 막고 있음

주의할 점도 있습니다.
- 현재 `If-Match`로 명시적으로 검증하는 건 리뷰 본체 변경 API 중심입니다.
- `Task`에도 `@Version`은 있지만, 지금 서비스에서 `Task`의 lockVersion을 별도 헤더로 비교하진 않습니다.
- 즉 `Task`는 현재 JPA 레벨 낙관락은 걸려 있지만, 리뷰처럼 API 헤더 기반 사전 검증까지는 아직 없는 상태입니다.

정리하면, 지금 코드의 낙관락은 "리뷰는 헤더로 한 번, JPA `@Version`으로 한 번" 검증하는 방식이고, 실제 버전 증가는 JPA가 자동으로 처리합니다.

## 17:52:45

### Question
방금 물어본거랑 포함해서 물어보면 if match는 현재 보낸 버전과 지금 진짜 버전이 맞는지 판별하는거지?

### Answer
네. 정확히는 그 뜻입니다.

`If-Match`는 클라이언트가 "내가 마지막으로 본 버전이 이 값이다"라고 보내는 값이고,
서버는 이 값이 현재 DB에 저장된 진짜 `lockVersion`과 같은지 확인합니다.

즉 판별하는 것은:
- 클라이언트가 보낸 버전
- 현재 DB의 실제 버전

이 둘이 같은가 입니다.

예를 들어 현재 DB의 `lockVersion = 1` 이라고 하면:

1. 사용자 A가 조회
- 응답에서 `lockVersion = 1` 을 받음

2. 사용자 B도 조회
- 역시 `lockVersion = 1` 을 받음

3. A가 수정 요청
- `If-Match: 1` 전송
- 서버가 DB 현재값 1과 비교
- 같으므로 통과
- 저장 성공 후 DB 버전이 `2`로 증가

4. B가 나중에 수정 요청
- 여전히 `If-Match: 1` 전송
- 그런데 DB 현재값은 이미 `2`
- 서버가 비교했을 때 다름
- 그래서 충돌로 판단하고 실패시킴

즉 `If-Match`는 "내가 보고 수정하려는 대상이 아직도 내가 본 그 상태가 맞는가"를 확인하는 장치입니다.

현재 코드 기준으로는 두 단계로 동작합니다.

1. 서비스 레벨 사전 검증
- `ReviewCommandService.validateLockVersion(review, lockVersion)`에서
- 헤더로 받은 `If-Match` 값과 현재 `review.getLockVersion()`을 비교합니다.
- 다르면 바로 `REVIEW_VERSION_CONFLICT`를 던집니다.

2. JPA `@Version` 최종 검증
- 엔티티의 `lockVersion` 컬럼에 `@Version`이 붙어 있어서
- 실제 update 시점에도 JPA가 버전 충돌을 한 번 더 막습니다.

그래서 한 줄로 요약하면:
`If-Match`는 클라이언트가 보낸 버전과 DB의 현재 실제 버전이 일치하는지 판별하는 용도이고, 같아야만 수정/승인/반려 같은 변경 작업을 계속 진행할 수 있습니다.
