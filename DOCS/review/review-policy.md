# 검토 도메인 정책 정리

## 1) 상태 전이 정책

- 검토는 업무가 `IN_REVIEW` 상태일 때 생성 가능하며, 생성된 검토의 최초 상태는 `SUBMITTED`로 한다.
  - 업무가 `IN_REVIEW` 로 변하는 것과, 검토가 생성되는 것은 같이 일어난다는 것은,
    1. 하나의 트랜잭션안에서 일어나거나
    2. 또는 결과적 정합성이 유지된다는(MSA 의 경우) 의미이다.
  - 업무의 상태를 `IN_REVIEW` 로 변경한 뒤에야 검토를 생성할 수 있다
- 유효한(`SUBMITTED`) 검토가 없을 때만 새로운 검토 생성 가능
- 검토 승인: `SUBMITTED -> APPROVED`
- 검토 반려: `SUBMITTED -> REJECTED` (반려 사유 필수)
  - `REJECTED` 상태인 검토의 상태는 더 이상 변경되지 않는다.
- 검토 재상신:
  - 재상신 시 기존 검토를 재사용하지 않음(새 검토 생성)
  - 해당 업무에 `REJECTED` 상태인 검토가 있는 경우에만 재상신이라고 부른다.
  - 검토 재상신 횟수 제한은 없음
- 검토 취소:
  - 제출 철회 의미로 정의하며, `SUBMITTED` 상태에서만 허용

## 2) 업무 상태 연동 정책

### 2-1. 검토 반려 시

- 검토가 `REJECTED` 되면 대상 업무 상태는 자동으로 `IN_PROGRESS`로 전환

### 2-2. 재상신 진입 트리거

- 업무가 `IN_PROGRESS` 상태가 된 이후 `IN_REVIEW`로의 전환은 작성자의 명시적 검토 상신/재상신 요청으로만 가능
- 검토 반려로 인해 업무가 `IN_PROGRESS`로 전환된 경우에도 동일하게 작성자의 재상신 요청을 통해 `IN_REVIEW`로 재진입

## 3) 변경 불가(락) 정책

### 3-1. 기본 원칙

- 승인 또는 반려 상태의 검토는 변경 불가 상태로 본다
- 전체 변경 불가 대상은 다음을 포함한다
  - 검토 본문
  - 첨부 자료
  - 참조자
  - 기존 코멘트

### 3-2. 수정 불가 범위

- 승인/반려 이후에는 오탈자 및 경미한 수정도 허용하지 않음
- 첨부 추가/수정/해제 불가
- 참조자 추가/해제 불가
- 기존 코멘트 수정/삭제 불가

### 3-3. 예외

- 승인/반려 이후에도 **신규 코멘트 작성은 허용**
- 단, 신규 코멘트 작성 가능은 후속 커뮤니케이션 목적의 예외이며, 기존 코멘트 수정 가능을 의미하지 않음

### 3-4. super 예외

- 관리자 예외 수정은 별도 권한으로 허용할 수 있음
- 관리자 예외 수정은 운영상 정정이 필요한 최소 범위에서만 허용한다
- 모든 관리자 예외 수정도 감사 로그에 반드시 남겨야 함

## 4-1) 검토 참조자 정책

- 참조자는 검토를 조회하고 코멘트를 남길 수 있는 사람을 뜻함
- 참조자 할당/해제는 권한자(작성자/관리자)만 가능
- 중복 할당 금지(다중 할당은 됨)
- 참조자 변경은 `SUBMITTED` 상태에서만 허용
- `APPROVED`, `REJECTED` 이후에는 참조자 변경 불가

## 4-2) 추가 검토자 정책

- 검토 승인/반려는 관련 권한을 가진 사람이 모두 가능
- 추가 검토자란, 그러한 권한이 없는 사람도 해당 검토에 대해 승인/반려 할 수 있도록 만들어주기 위한 기능
- 이를 통해서 권한이 부여되지 않은 담당자가 승인/반려할 수 있도록 만들어 줄 수 있음

## 5) 검토 자료 정책

- presigned url 사용 고려
- 첨부 파일 확장자/용량/개수 제한 적용
  - 확장자 없는 것도 허용
  - 문서(`.txt`, `.pdf`, `.docx`, `.md`, `.hwp` 등)
  - 이미지(`.jpg`, `.jpeg` 등)
- 첨부 변경은 별도 버전 개념으로 분리하지 않고 “첨부 수정”으로 간주
- 승인/반려 이후 첨부 변경 불가

## 6) 검토 코멘트 정책

### 6-1. 기본 원칙

- 코멘트는 공식 검토 내용을 대체하거나 수정해서는 안 된다
- 코멘트는 후속 커뮤니케이션 용도로만 사용
- 코멘트는 작성자, 참조자, 검토자만 작성할 수 있다.

### 6-2. 작성/수정/삭제

- 코멘트 작성/수정/삭제에 대한 히스토리를 남겨야 하나, 1차 MVP 에서는 수정 히스토리에 대해 “편집됨” 표시를 남길 수도 있다.
- 승인 후 기존 코멘트는 수정 불가, 새로운 코멘트를 달 수는 있다.
- 승인 이후 코멘트 삭제는 허용하지 않음
- 반려 이후 코멘트 작성/수정/삭제 불가

## 7) 검토 취소 정책

- 검토 취소는 제출 철회로 정의
- `SUBMITTED` 상태에서만 가능
- 승인/반려 이후에는 검토 취소 개념을 두지 않음
- 취소된 검토는 승인/반려 이력과 구분되는 별도 이벤트로 기록

## 8) 동시성 및 상태 충돌 정책

- 승인 요청 직전 본문/첨부/참조자 등 검토 본체(코멘트 제외)가 수정되면 승인 요청은 실패해야 함
- 동시성 이슈
  - 승인 + 수정
  - 승인 + 승인
  - 승인 + 반려
  - 반려 + 반려
  - 승인 + 코멘트
  - 반려 + 코멘트
- 참조자 변경과 승인 요청이 동시에 발생한 경우, 저장이 먼저 완료된 최신 version 기준으로 승인 가능 여부를 판단
- 이미 `REJECTED` 된 검토에 대한 직접 승인 요청은 허용하지 않음
- 반려 이후에는 업무가 `IN_PROGRESS`로 전환되며, 다시 제출되어 `SUBMITTED` 상태가 된 뒤에만 승인 요청 가능

## 9) 감사 로그(=히스토리) 정책

- 상태 전이 감사 로그는 필수
- 최소 기록 항목:
  - actor(who)
  - time(when)
  - action(event/how)
  - reason(why)
  - 대상 ID(what)
    - 예: 업무, 검토
- 다음 이벤트도 가능한 한 **유형**으로 나눠서 세세하게 기록
  - 검토 생성
  - 검토 승인
  - 검토 반려
  - 검토 취소
  - 참조자 할당/해제
  - 검토자 할당/해제
  - 첨부 추가/취소
  - 코멘트 생성

## 10) 알림/실시간 정책

- 현재 단계에서는 알림 정책은 범위에서 제외
- 다만 향후 알림/실시간 전송 방식과 무관하게 도메인 이벤트 및 감사 로그 정책은 먼저 확정해야 함

## 핵심 원칙 요약

1. 반려되면 업무는 자동으로 `IN_PROGRESS`로 돌아간다.
2. 현재 유효한 승인은 현재 업무에 연결된 마지막 `APPROVED` 검토만 인정한다.
3. 승인/반려 이후에는 전체 락을 적용하되, 신규 코멘트 작성만 예외적으로 허용한다.
4. 코멘트는 공식 검토 내용을 대체하지 않는다.
5. 승인 후 작성된 코멘트는 기존 승인 사실을 변경하거나 대체하지 않는다.
6. 관리자 예외 수정 중 승인 판단에 영향을 주는 변경은 기존 승인 효력을 상실시킨다.
7. `IN_PROGRESS -> IN_REVIEW` 전환은 항상 작성자의 명시적 재검토 요청으로만 가능하다.
8. 승인 이후 검토 취소는 없으며, 이후 변경은 업무 롤백 + 재검토 사이클로만 처리한다.
