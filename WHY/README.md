# WHY

이 폴더는 로컬 전용 ADR(Architecture Decision Record) 보관소다.  
즉, "무엇을 만들었는가"보다 "왜 이런 선택을 했는가"를 남기는 곳이다.

## 이 폴더에 기록하는 것

- 기술, 라이브러리, 패턴, 인프라 도구를 채택하거나 제외한 이유
- 특정 구현 방식, 모델링 방식, API 규칙, 운영 방식의 결정 이유
- 대안 비교, 트레이드오프, 제약사항, 이후 영향

## ADR처럼 쓰는 기준

한 문서는 하나의 결정만 다룬다.  
문서에는 아래 항목이 들어가야 한다.

1. `상황(Context)`
   왜 이 결정을 내려야 했는지, 당시의 문제와 제약을 적는다.
2. `결정(Decision)`
   최종적으로 무엇을 선택했는지 한 문장으로 명확히 적는다.
3. `근거(Why)`
   이 결정을 선택한 핵심 이유를 적는다.
4. `대안(Alternatives)`
   검토했지만 채택하지 않은 선택지와 제외 이유를 적는다.
5. `결과(Consequences)`
   얻는 이점, 감수하는 비용, 이후 파생 작업을 적는다.

가능하면 아래 메타데이터도 함께 남긴다.

- `상태`: Proposed / Accepted / Superseded / Deprecated
- `작성일`
- `관련 문서`: PLAN, DOCS, 코드 경로, 이슈 링크

## 권장 템플릿

```md
# [제목]

- 상태: Accepted
- 작성일: YYYY-MM-DD
- 관련 문서: [문서명](../DOCS/...)

## 상황

## 결정

## 근거

## 고려한 대안

## 결과

## 후속 작업
```

## 작성 규칙

- 파일명은 `<기술명>.md` 또는 `<기능명>-why.md` 형식을 우선 사용한다.
- 구현 설명보다 결정 이유와 트레이드오프를 우선 적는다.
- "좋아서", "익숙해서" 같은 표현으로 끝내지 말고 팀 기준으로 설명한다.
- 나중에 결정을 뒤집을 수 있도록 당시의 제약과 판단 기준을 남긴다.
- 꼬리 질문이 예상되면 문서 하단에 Q&A 형태로 덧붙여도 된다.

## 꼬리 질문 정리 방식

기술적인 이유를 적고 끝내지 말고, 면접이나 리뷰에서 나올 만한 왜를 더 파고든다.

- 왜 이 대안을 버렸는가
- 왜 지금은 맞지만 나중에는 아닐 수 있는가
- 운영/성능/협업 측면에서 어떤 비용이 생기는가
- 이 결정이 데이터 모델, API, 배포에 어떤 영향을 주는가

필요하면 웹 검색을 통해 실제로 자주 나오는 질문을 기준으로 3~5개 정도의 후속 질문과 답을 정리한다.

## 주의

- 이 폴더의 내용은 로컬 전용이다.
- 커밋, 푸시, PR에 포함하지 않는다.
